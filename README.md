# snishka

[English](README.en.md) | [Русский](README.md)

Скилл автоматизирующий поиск SNI, который проходит сквозь **фильтрацию по объёму трафика (16-20Кб блок)**.
Может быть использован для реанимирования Hetzner, OVH, DigitalOcean и других зарыбленных машин, к которым есть доступ по ssh

Работает как **скилл для Claude Code** и как **самостоятельная CLI-утилита**
(`python3 snihunt.py …`) — Claude не обязателен.

---

## Проблема

Бывает так: сервер жив — ssh, пинг и TLS-handshake до него проходят, IP **не
забанен**, — а VPN не поднимается. Частая причина: DPI фильтрует не по IP, а по
**SNI в связке с объёмом**. ClientHello с «неопознанным» SNI проходит, хендшейк
даже завершается, но после ~16–20 КБ данных соединение душится (дроп/таймаут).
SNI из «белого списка» провайдера идут без ограничений.

Reality маскирует трафик под `dest`/`serverNames`. Если это имя не в белом
списке — VPN умирает ровно на лимите объёма.
Ключевой факт: **в тех же подсетях живут whitelisted-хосты** — крупные ресурсы,
чьи имена провайдер пропускает.

## Как это работает

Главный принцип: проверять надо **не «открывается ли сайт-владелец SNI»**, а
сколько данных прокачивается **на боевой IP твоего сервера** с этим SNI. Первое
меряет путь до чужого адреса и врёт. Второе — ровно тот путь, что пройдёт VPN.

Отсюда конвейер:

1. **discovery** — собрать домены-кандидаты из соседних подсетей хостера
   (по сертификатам) или из Certificate Transparency;
2. **serve** — поднять на боевом сервере TLS-эндпоинт, отдающий большой ответ на
   **любой** SNI;
3. **rutest** — с аплинка за DPI качать этот эндпоинт, подставляя разные SNI, и
   ловить, кто пробил порог объёма (whitelisted), а кого задушило на ~16 КБ;
4. **qualify** — отобрать прошедшие, которые ещё и годятся как Reality `dest`
   (TLS 1.3 + X25519 + h2, отдают `200` без редиректа).

## Быстрый старт

```bash
S=skill/scripts/snihunt.py

# 1. домены-кандидаты из подсетей хостера (см. дисклеймер про abuse ниже!)
python3 $S prefixes --asn <ASN-хостера> --near <своя-подсеть/24> --limit 24 > nets.txt
python3 $S scan --cidr-file nets.txt --conc 150 --bind <IP-аплинка> --out alive.txt
python3 $S certs --in alive.txt --conc 60 --out certs.jsonl
python3 $S domains --in certs.jsonl > domains.txt

# 2. тестовый эндпоинт на боевом сервере (отдаёт 2 МБ на любой SNI)
python3 $S serve --bind-ip <боевой-IP> --port 8000 --size 2097152

# 3. перебор с аплинка за DPI — ядро метода
python3 $S rutest --domains-file domains.txt \
    --dst-ip <боевой-IP> --bind <IP-аплинка> \
    --mode bulk --bulk-port 8000 --need-bytes 262144 \
    --rounds 3 --conc 4 --delay 0.4 \
    --control-good <заведомо-whitelisted-домен> --control-bad nonexistent.invalid \
    --out verdict.jsonl

# 4. отчёт
python3 $S report --in verdict.jsonl --only-pass
```

## Как читать вердикт

Качаем `need-bytes` данных с боевого IP, подставляя проверяемый SNI:

| Вердикт | Что значит |
|---|---|
| `whitelisted` | прокачали весь объём — SNI проходит throttling ✅ |
| `throttled` | оборвалось на ~16–20 КБ — след лимита по объёму |
| `blocked` | 0 байт / хендшейк не прошёл |
| `tcp_fail` | TCP не открылся; обычно шум от своей же нагрузки на цель |

Контрольные домены (`--control-good` / `--control-bad`) печатаются перед
прогоном. Если заведомо whitelisted-контроль сам не проходит — замер невалиден
(не тот канал/фаза), а не «SNI плохой». Верь только результатам, стабильным во
всех раундах.

## Отбор под Reality `dest`

Прошедший фильтр SNI ещё должен годиться как маскировочный хост: TLS 1.3,
согласование на X25519, ALPN `h2`, отдаёт `200` без редиректа на посторонний
домен, крупный и стабильный сайт, в идеале — та же страна/хостер, что и сервер.
Это проверяет подкоманда `qualify`.

## ⚠️ Про abuse и легальность

Этап discovery умеет активно сканировать 443 по подсетям хостера. **Это
сканирование сетей, которыми ты не владеешь:**

- нарушает ToS большинства хостеров;
- провоцирует abuse-репорт. Крупные хостеры (Hetzner, OVH и др.) детектят
  netscan к своим диапазонам и могут **залочить сервер**;
- **особенно опасно запускать скан на VPS того же хостера, чью сеть сканируешь** —
  это кратчайший путь к abuse и локу.

Поэтому команда `scan` требует явного подтверждения риска (интерактивно или
флагом `--accept-abuse-risk`). Менее рискованная альтернатива для discovery —
брать домены из **Certificate Transparency** (crt.sh) без единого пакета в чужую
сеть.

Ответственность за легальность и последствия использования — на пользователе.
Запускай активные проверки только против **своей** инфраструктуры или там, где у
тебя есть явное разрешение владельца.

## Оговорки

- TLS-отпечаток проб — питоновский, не браузерный. DPI, смотрящий на fingerprint
  (а не только на SNI/объём), этим методом не воспроизводится.
- Проверяется старт соединения и объём; блокировку по поведению на длинной сессии
  метод не увидит.
- Белые списки и фазы фильтрации меняются со временем и по регионам — список
  рабочих SNI недолговечен, перепроверяй перед боевым применением.
- При нескольких аплинках всегда указывай `--bind` на нужный интерфейс, иначе
  замер уедет на маршрут по умолчанию.
