# Поиск whitelisted-SNI под РФ-DPI (throttling по объёму)

## Зачем это нужно

Метод позволяет **раскурить (реанимировать) хостинг, зарыбленный по SNI** — то
есть площадку, где твой IP формально жив (ssh/пинг/TCP-handshake проходят), но
любой VPN-трафик душится, потому что РФ-DPI режет по SNI+объёму, а не по IP.
Под это попадают целые дата-центры: **Hetzner, OVH** и прочие популярные у
VPN-щиков хостеры — их подсети провайдеры не банят целиком (там же лежит куча
легального), но давят весь неопознанный TLS к ним throttling'ом.

Фокус в том, что **в тех же зарыбленных подсетях живут whitelisted-хосты** —
крупные РФ-ресурсы (например `2ip.ru` физически на Hetzner). Их SNI провайдер
пропускает без ограничений. Найдя такой SNI и поставив его как Reality `dest`,
ты прячешь свой VPN за «одобренным» именем в той же сети — и сервер, который
казался мёртвым, снова работает. То есть методика превращает «этот хостинг не
работает под VPN в РФ» в «работает, если взять правильный SNI-сосед».

Практический выхлоп: рабочий список `dest`-кандидатов под конкретный
хостинг+провайдера, отсортированный по пригодности для Reality.

## Когда это применимо

Симптом: VLESS+Reality на сервере не работает, **хотя IP не забанен** — ssh,
пинг и TCP-handshake до сервера проходят. Классическая ошибка — думать, что
нужно менять IP. На деле провайдер (мобильный или домашний РФ) применяет
**фильтр по SNI с лимитом объёма**: ClientHello с «неодобренным» SNI проходит,
хендшейк даже завершается, но после ~16-20 КБ данных соединение душится (дроп/
таймаут). SNI из «белого списка» (обычно крупные РФ-ресурсы: `2ip.ru`,
`text.ru`, `aliexpress.ru`, банки, VK/Яндекс-домены) идут без ограничений.

Reality маскирует трафик под `dest`, поэтому если dest-SNI не в белом списке —
VPN мрёт ровно на этом лимите. Задача скилла: найти SNI, который **у данного
провайдера** проходит без throttling, и при этом пригоден как Reality dest.

Есть и более грубая разновидность блокировки — **фильтр по IP** (типично для
мобильных модемов: whitelisted-подсети проходят, остальные дропаются на уровне
IP/ICMP). Её подбором SNI не обойти — сначала классифицируй, с чем имеешь дело
(шаг 1). Механики различаются между аплинками одного и того же места (WiFi ≠
модем), поэтому всегда привязывайся к конкретному интерфейсу через `--bind`.

## Ключевой принцип замера

Проверять надо **не «открывается ли сайт-владелец SNI из РФ»**, а сколько
данных прокачивается **на боевой IP твоего сервера** с этим SNI. Первое меряет
путь до чужого IP и врёт. Второе — ровно тот путь, что пройдёт VPN.

Отсюда весь метод строится вокруг одного трюка: поднять на боевом сервере
TLS-эндпоинт, который отдаёт большой ответ на **любой** SNI, и с российского
аплинка качать его, подставляя разные SNI. Кто пробил порог (напр. 256 КБ) —
whitelisted.

## ⚠️ Про abuse (читать до сканирования)

Этап сбора доменов включает скан 443 по чужим подсетям хостера. **Никогда не
запускай этот скан с боевого сервера самого хостера** — прилетит abuse-репорт
на аккаунт (проверено на практике: Hetzner детектит netscan к своим же
диапазонам и грозит локом сервера). Варианты:

- сканировать с российского аплинка (`ssh home`) — тогда abuse, если и придёт,
  то домашнему провайдеру; плюс это заодно тест (см. ниже);
- взять домены из Certificate Transparency (crt.sh) / Censys — вообще без скана;
- если сканируешь — низкий rate, и осознавай, чей IP светится источником.

Скан **портов** (TCP-connect) с российского аплинка обычно проходит сквозь DPI.
А вот **сбор сертификатов** (полный TLS) через DPI душится — с home соберётся
лишь ~20% сертов против ~76% из ДЦ. Это само по себе диагностика, но для полного
списка доменов сбор сертов лучше делать из места без DPI (любой **не тот же**
хостер), либо мириться с неполнотой.

## Инструмент

Всё делает `scripts/snihunt.py` (без внешних зависимостей кроме `cryptography`,
которая обычно уже стоит). Подкоманды — это конвейер; см. `--help` у каждой.
Разложи так: тяжёлые этапы (`prefixes/scan/certs/qualify`) — с быстрого хоста
без DPI; `serve` — на боевом сервере; `rutest/report` — с российского аплинка.

Запускать python-скрипт можно прямо через ssh на нужный хост. Скопируй
`scripts/snihunt.py` на оба конца (боевой сервер и российский аплинк) один раз.

### Конвейер

```bash
# 1. КЛАССИФИКАЦИЯ. Сначала пойми механику. С российского аплинка:
#    - TCP-connect до боевого IP жив? Если нет — блок по IP, SNI не поможет.
#    - bulk-проба (ниже) с заведомо whitelisted SNI (2ip.ru) должна пробить
#      порог, а с мусорным (nonexistent.invalid) — зависнуть на ~16 КБ.
#    Контроли обязательны: если whitelisted-контроль сам не проходит —
#    замер невалиден (не та фаза/канал), а не «SNI плохой».

# 2. ДОМЕНЫ-КАНДИДАТЫ. Префиксы хостера рядом со своей подсетью:
python3 snihunt.py prefixes --asn <ASN-хостера> --near <своя-подсеть/24> --limit 24 > nets.txt
#    Скан 443 (см. предупреждение про abuse — НЕ с сервера хостера):
python3 snihunt.py scan --cidr-file nets.txt --conc 150 --bind <IP-аплинка> --out alive.txt
#    Домены из сертификатов (дефолтный vhost, без SNI):
python3 snihunt.py certs --in alive.txt --conc 60 --out certs.jsonl
#    Уникальные домены, РФ-зоны первыми (белый список — это РФ-ресурсы):
python3 snihunt.py domains --in certs.jsonl > domains.txt

# 3. ТЕСТОВЫЙ ЭНДПОИНТ на боевом сервере (отдаёт 2 МБ на любой SNI):
#    открой порт в firewall и подними serve на боевом IP.
python3 snihunt.py serve --bind-ip <боевой-IP> --port 8000 --size 2097152

# 4. ПЕРЕБОР с российского аплинка — ядро метода. Качаем эндпоинт, меняя SNI,
#    и ловим, кто пробил порог. --bind обязателен при нескольких аплинках.
python3 snihunt.py rutest --domains-file domains.txt \
    --dst-ip <боевой-IP> --bind <IP-аплинка> \
    --mode bulk --bulk-port 8000 --need-bytes 262144 \
    --rounds 3 --conc 4 --delay 0.4 \
    --control-good 2ip.ru --control-bad nonexistent.invalid \
    --out verdict.jsonl

# 5. ОТЧЁТ + отбор пригодных под Reality (см. ниже):
python3 snihunt.py report --in verdict.jsonl --qualified candidates.jsonl --only-pass
```

## Как читать вердикт (режим bulk)

Качаем `need-bytes` данных с боевого IP, подставляя проверяемый SNI:

| Вердикт | Что значит |
|---|---|
| `whitelisted` | прокачали весь объём — SNI проходит throttling ✅ |
| `throttled` | оборвалось на ~16-20 КБ — классический след лимита по объёму |
| `blocked` | 0 байт / хендшейк не прошёл |
| `tcp_fail` | TCP не открылся; обычно шум от своей же нагрузки на цель |

`tcp_fail` лечится снижением `--conc` и `--delay` — все пробы бьют в один IP,
пачкой легко получить ложные обрывы. Гоняй ≥3 раунда и верь только `stable`
(прошло во всех раундах). Порог `--need-bytes` бери с запасом над лимитом
(512 КБ надёжнее 256, чтобы отсеять флуктуации).

Есть и режим `--mode handshake` (только ClientHello) — он отвечает лишь на
вопрос «дошёл ли пакет», но НЕ ловит throttling по объёму. Для этой блокировки
нужен именно `bulk`.

## Отбор под Reality dest

Прошедший DPI SNI ещё должен годиться как `dest`. Хороший кандидат:

- **TLS 1.3 + согласование на X25519** (`openssl s_client -tls1_3 -groups X25519`
  должен дать `CONNECTION ESTABLISHED`);
- **ALPN h2**, отдаёт `200` без редиректа на посторонний домен;
- валидный сертификат; сайт крупный и стабильный;
- в идеале — та же страна/хостер, что и твой сервер (меньше палится geo-mismatch).

Подкоманда `qualify` проверяет это автоматически; финальный ручной прогон
кандидата — `openssl s_client` + `curl --http2 --resolve` к самому домену
(одиночные коннекты, не скан).

## Оговорки

- TLS-отпечаток проб питоновский, не браузерный. DPI, смотрящий на fingerprint
  (а не только на SNI/объём), этим методом не воспроизводится.
- Проверяется старт соединения и объём; блокировку по поведению (тайминги,
  паттерн трафика на длинной сессии) метод не увидит.
- Белые списки и фазы меняются со временем и по регионам — список рабочих SNI
  недолговечен, перепроверяй перед боевым применением.
- Механика различается между WiFi и мобильным модемом одного места — всегда
  `--bind` на нужный интерфейс, иначе замер уедет на маршрут по умолчанию.
